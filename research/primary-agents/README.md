# Choosing the primary coding agent in a Factory sandbox

**Recommendation.** Add one choice to the first creation screen, **Coding agent**, defaulting to **Pi**. A native Codex, Claude Code or Antigravity CLI can drive a Factory-managed Chromium session. All three also accepted a model endpoint controlled by Factory in API-key mode. The important product decision is how someone wants to pay and sign in. A vendor subscription login and a protected API connection have different security properties.

This is a local design experiment. The tests use the real CLI binaries, a disposable Linux container and a deterministic model response that requests a specific tool. The browser, client tool dispatch, host viewer and policy hooks are real. Synthetic responses make no claim about how often a model would choose the tool on its own.

## What someone creating a sandbox would see

1. **New sandbox.** Choose the workspace and coding agent. Leaving Pi selected shows the existing Pi profile and preserves its defaults. Selecting another agent removes the Pi profile selector. Image and package selection happen automatically.
2. **Review sandbox.** Put **Sign-in** first and expand it when a connection is needed. Offer **Use a saved API connection** or **Sign in when I open the terminal**. Show **Copy host sign-in** only for a supported, detected credential that the user explicitly chooses. For an account session, explain in one line that programs running as the sandbox user may use it. For the protected option, show the provider and that usage is billed to its API account. Never silently choose API billing for someone who selected their subscription.
3. Show the common settings below that choice. A user who wants only Codex with the existing workspace can select Codex, accept terminal sign-in, and create. Someone who needs Claude Code with restricted network and a visible browser can select a saved Anthropic API connection and enable **Browser** on the same review screen.
4. **Open terminal** launches the selected native CLI in the configured starting directory. Use its normal sign-in and resume flow. Settings can change the connection, folders, network, SSH, Git, AWS or browser. To switch the primary agent, use **Create from existing** with a fresh private home and a fresh sign-in choice. This avoids silently moving account sessions or treating one agent's conversation history as another's.

| Reuse across agents | Show only when applicable |
|---|---|
| Workspace, read-only and writable mounts, starting folder, outer container, resources, outbound gateway and lifecycle | Pi profiles, Pi model providers, FrostPi, Pi extensions, recall, advisor orchestration and automatic reviewer stay in the Pi flow |
| Git identity, configured SSH destinations and the existing SSH companion, scoped AWS access and its companion | Use each CLI's own approvals. Only expose a native preference with a tested equivalent |
| Optional Chromium and the host viewer | Register the browser with the chosen client only when enabled |
| Shared network policy and the list of permitted destinations | Native web search gets a separate control. Pi search-provider configuration belongs to Pi |

## Authentication and credential containment

| Agent | Protected API connection tested with a placeholder | Personal account |
|---|---|---|
| Codex | Custom Responses provider, base URL and placeholder environment key. The CLI completed a streaming turn. | The CLI supports device login and documented transfer of file-backed sign-in. Offer direct login, with explicit host copy only for supported file storage. Treat the copy as an account credential inside the sandbox. [OpenAI authentication](https://developers.openai.com/codex/auth/) |
| Claude Code | Anthropic Messages endpoint through `ANTHROPIC_BASE_URL` with a placeholder key. Start with a clean credential store in this mode. | Let the user sign in through the unmodified Claude CLI. Omit Factory-managed subscription import and OAuth proxying from the new flow. Anthropic distinguishes user sign-in from applications collecting or intermediating subscription credentials. The existing advisor importer is not a basis for extending that behavior. [Gateway configuration](https://code.claude.com/docs/en/llm-gateway) · [Anthropic’s authentication terms](https://code.claude.com/docs/en/legal-and-compliance) |
| Antigravity | `modelProvider=gemini`, `GEMINI_API_KEY` set to a placeholder and `GOOGLE_GEMINI_BASE_URL` pointed at the fixture. Account sign-in and Gemini API billing are separate choices. | The host CLI completed a live request after sign-in. Factory already has a Linux advisor importer for one Secret Service item. A private sandbox keyring prevents a host-keyring mount, but programs with access to the unlocked sandbox session can use it. Prefer native login. Validate account refresh, revocation and provider terms before offering host copy. [Google authentication](https://antigravity.google/docs/install?tab=cli) |

**How to protect a key.** Reuse Factory’s private inference companion. The client gets a local endpoint and a placeholder. Only the companion gets the real key and a fixed upstream route. Give each sandbox access only to its assigned connection. Preserve vendor streaming and required headers and replace client authorization at the boundary. Codex needs Responses, Claude needs Messages and Google needs Gemini generation paths including auxiliary model requests. Restrict allowed operations, model destinations and credential injection in the companion. An authorized program in the sandbox can still consume the assigned service or send data to the model.

There are two pieces of experimental evidence here. All three CLIs worked against local vendor-protocol fixtures. Separately, Factory's existing two-container test authenticated an upstream stream, withheld the key and its volume from the client and passed again after a broker restart. A complete vendor turn through Factory’s shipping broker for each engine, including reconnect, streaming errors and vendor-specific tools, remains an implementation acceptance test.

**Can a subscription credential be protected too?** Local sign-in or copying makes the credential available to the native client. A private home, file permissions and a keyring separate users but do not isolate arbitrary code running with the same authority. A stronger design is to run the signed-in client in a trusted companion and give it a separate tool executor. Every file operation, shell, hook, plugin and browser tool would need to cross that boundary. The current advisor container achieves separation by giving the advisor no workspace tools. Promoting it unchanged would lose the behavior people want from a primary agent. Codex exposes an experimental remote execution interface worth evaluating independently. No protected, full-featured subscription configuration was established for the three CLIs. Keep that choice out of the initial design.

## Search, browser and sandbox instructions

| Client | Native web search | How the CLI received the sandbox context |
|---|---|---|
| Codex | Switching `web_search` from `disabled` to `live` added `web_search` to the outbound Responses request. The documented cached option is a distinct choice. | `developer_instructions` added the Factory marker while the project’s own `AGENTS.md` marker was also present. [CLI features](https://developers.openai.com/codex/cli/features/) |
| Claude Code | Denying `WebSearch` and `WebFetch` removed both from the Messages tool list. The control run offered both. Keep search and fetching distinct where the user needs separate permissions. | `--append-system-prompt-file` retained the Factory marker and the project’s `CLAUDE.md` marker. Disabling project settings wholesale lost the latter in the initial check. [CLI reference](https://code.claude.com/docs/en/cli-reference) · [Permissions](https://code.claude.com/docs/en/permissions) |
| Antigravity | The native `search_web` tool was offered. A global `PreToolUse` hook matched it and returned a denial. The CLI passed the denial back to the model. The tool remains advertised. This is a managed CLI preference, not a system-wide network boundary. | A private-home global `~/.gemini/AGENTS.md` and the project’s `AGENTS.md` both reached the main model request. [Google hooks](https://antigravity.google/docs/hooks?tab=cli) · [Rules](https://antigravity.google/docs/rules/) |

Generate one short context block from the effective sandbox configuration. Include the starting directory, mounted paths and permissions, the actual network policy, and the browser tool only when enabled. Put it in the client-specific additive location. Keep project documents intact. Include no bearer links, keys or cookies. Context tells the model how to work. Mounts, the gateway and credential companions enforce the permissions.

The gateway controls traffic that originates in the sandbox. A vendor can perform web search remotely during an allowed model request. A restricted subnet or site allowlist therefore cannot promise to filter those results. If the user requires searches restricted to their allowed sites, disable unfiltered vendor search and offer a browser that actually uses the gateway. CLI preferences can be changed by code with the same privileges unless Factory owns and enforces the corresponding policy outside the writable home.

**Which browser?** For a terminal sandbox, provide the existing Factory Chromium. A text search result has no visible tab. Claude's desktop Chrome integration expects its extension and a desktop browser. Google’s native CLI browser integration has its own Chrome discovery, debugging and confirmation requirements. There is no need to introduce a host browser profile or require a Codex desktop plugin. [Claude Code with Chrome](https://code.claude.com/docs/en/chrome) · [Antigravity browser](https://antigravity.google/docs/browser?tab=cli)

The experiment registered a small standard-input/output MCP server backed by Factory’s existing browser runtime. Codex called a namespaced tool, Claude called its MCP tool directly, and Antigravity used its lazy MCP dispatcher. In each case the browser opened a synthetic document and clicked its button. A host-side check found that document's title over the signed loopback viewer and negotiated a VNC session while the tool was active. The updated button value then reached the CLI's next model request. A system message alone cannot install, register or authorize this tool. A production adapter should keep the browser alive independently of one MCP connection so users can inspect it after a turn or reconnect.

## Implementation boundary and evidence

Persist a primary-agent choice with the sandbox snapshot. Build a shared CLI environment with only the selected agent layer. Use the existing advisor binaries and pinning where appropriate. The launcher can select the executable, login method, instruction location, search setting and MCP registration from that choice. The existing lifecycle, network, AWS, SSH and viewer owners should continue to enforce their own policies. Leave the Pi path as the default and exercise existing Pi and FrostPi launches before shipping any future implementation.

Opus reviewed the proposed design. Its main objection was that a common agent selector could imply identical security and features. The proposed creation flow addresses that by showing only the sign-in and tools available for the chosen CLI. Its suggestion to distinguish vendor search from local browsing was borne out by the tool-level tests. The browser experiments also established something a design review alone could not show: all three terminal clients can drive the same visible browser.

The original offline runs used Codex 0.171.0, Claude Code 2.1.319 and Antigravity 1.5.0. All three produced their native interactive screens in a pseudo-terminal. A second run from a fresh container with Antigravity 1.5.13 passed all three browser, context and search checks. The synthetic Codex provider produced a fallback model-metadata notice and completed its turns. Factory’s viewer and credential-import unit suites passed 19 tests. The separate broker test passed before and after restart. Live subscription verification was limited to a short Antigravity host request with version 1.5.13. The experiment did not exercise live subscription refresh in a primary sandbox, interactive keyboard takeover through noVNC, a complete vendor billing cycle, macOS or WSL. No account credentials were copied into the research containers.

### Repeat the offline experiment

From the checkout root, set `DEV_IMAGE` to a locally built browser-enabled Factory dev image. Set `CODEX_BIN`, `CLAUDE_BIN` and `AGY_BIN` to absolute paths to the native Linux executables. Run `sh research/primary-agents/run.sh` on a host with Podman. It uses a disposable workspace and private home, binds the executables and fixtures read-only, and runs with the external network disabled. The final checks inspect the client requests for the expected controls and tool results. The launcher removes its container on exit.

The separate credential test is `python3 tests/inference_container.py --image <local-inference-image> --dev-image <local-dev-image>`. It creates and removes its own containers and volumes using synthetic credentials.
